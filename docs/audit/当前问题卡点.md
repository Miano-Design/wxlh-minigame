## 一、P0 · 关卡结算页：真奖励面板被"晚到的收尾"盖成兜底

**现象**：打完一关，结算页显示「结算数据不在了 · 先回世界」——**没有奖励胶囊、没有获得道具**，
但奖励其实已经发了（背包里能看到）。自动下一关（`› 下一关（…）5s`）现在是好的。

**证据（真机控制台逐行时序，一场打完）**：

```
 battle · end              ← 第 1 次收尾（真的）
 battle · clear stage=1
 event · dungeon_clear
 dun · null@settleRun      ← 真结算跑完，run 被正常清空（这一步是对的）
 battle · end              ← ★ 又来了几次
 dun · resort hadRun=false ← 它们走兜底分支，把真面板盖掉
 battle · end ×2
 battle · clear stage=2    ← 自动下一关一直在工作
```

**我已经查到的**：

- `sc-dungeon.js` 的 `onEnd()` 里有一条 `if (!run) return lastResortPanel(win)`；
  晚到的那几次收尾此时 `run` 已空 ⇒ 返回兜底 ⇒ `sc-battle` 的 `finish()` 把它当成新面板 ⇒ **盖掉真面板**。
- `finish()` 自己有 `if (B.done) return` 的闸，所以那几次 `battle · end` 不是"同一场重复 finish"，
  而是**另一个/另一次 onEnd 走到这里**。
- 已经在 `fightWave()` 里把这一场钉进闭包（`myRun`），但晚到那几次里 `myRun` **也是空的**
  ⇒ 说明那次 `fightWave` 起跑时模块级 `run` 就已经是空的了（**这里还没钉死**）。

**已加的四道闸**（都还在，未能收回真面板）：

1. `onEnd` 里 `run` 空了但 `myRun` 在 ⇒ 认回来；
2. 真面板记进 `lastPanel`，再进来把真面板还回去；
3. `lastPanel` 不再被 `clearSettleTargets()` 清（只在开新一场时作废）；
4. `finish()` 里：晚到那张如果比已显示过的更空，就不认它。

**下一轮建议的第一步**：在 `startStage()` 里把这一场的 `run` **另挂一份到不会被清的地方**
（例如 `B.dungeonRun` / `Dun.current`），收尾只认那一份 —— 晚到几次也永远拿得到真数据。
第二步：查清"为什么会有多次晚到的 `battle · end`"（谁在结算之后再触发一次收尾），
从源头去掉，而不是继续加闸。

### 1.1 2026-10-03 晚 · 又一轮实测（**证据比上一轮更硬**）

**现象**：打完一关（怨声旧宅 第 1/12 关 · 第 3/3 波）结算页显示
「3 回合 · 结算数据不在了 · 先回世界」，**没有奖励胶囊**；
但四颗按钮全在，且「› 下一关（怨声旧宅 2/12） 2s」**倒计时在走**（自动下一关是好的）。

**这一轮埋点拿到的东西（都在一条真机上跑出来的日志里）**：

```
dun · onend win=true hasRun=true hasMy=true wave=0 waves=3 stage=1 last=false rounds=1
dun · onend win=true hasRun=true hasMy=true wave=1 waves=3 stage=1 last=false rounds=3
dun · onend win=true hasRun=true hasMy=true wave=2 waves=3 stage=1 last=false rounds=1
dun · onend win=true hasRun=true hasMy=true wave=0 waves=3 stage=2 last=false rounds=1
```

读法：
- **波次机器是对的**（stage1 依次 0/1/2 波，然后 stage2 从 0 波开始）；
- 每一次 `onEnd` 进来 `run` **都在**（`hasRun=true`、`hasMy=true`）——
  也就是说**这一轮没有走"run 空 ⇒ 兜底"那条路**；
- 但在另一轮里我明确看到过 `dun · resort win=true hadPanel=false hadRun=false`，
  以及 `dun · null@settleRun`（`settleRun` 确实跑到过 `run = null` 那一行）。
  ⇒ **同一条链上，两种状态都出现过**（有时 run 在、有时 run 空），不是稳定复现。

**我这一轮加过的三道保险（都还在代码里）**：
1. `fightWave()` 把这一场钉进闭包（`myRun`），`onEnd` 发现 `run` 空了就认回来；
2. `settleRun` 的真面板记进 `lastPanel`，再进来把真面板还回去（`lastPanel` 只在**开新一场**时作废）；
3. **三块装饰各自包 try**（首通庆祝 / 线索行 / 战场变化）——炸了就少那一行，不许带走整张面板。

**我试过但没能定论的**：日志缓冲太小（`get_simulator_console` 只能拿到最后 ~30 行），
而这条链每次战斗要打 3 波、每波都发好几条账 —— **`dun · resort` 那条关键账很可能被后来的日志冲掉了**。
所以"到底是谁把 `run` 清空 / 谁让 `settleRun` 没跑"这一问，我**没有拿到决定性的一行日志**。

**给 GPT 的下一步（我建议按这个顺序，别再加补丁）**：
1. 把 `dun · onend` / `dun · settle_panel` / `dun · resort` 三条账**改成写进存档里的一个短环形缓冲**
   （`S.diag.trace`，最近 20 条），而不是只进 console —— 这样打完一关可以**事后读档**看整条时序，
   不受日志缓冲大小影响；
2. 拿到那条时序后**从源头去掉**"晚到的 onEnd"（谁在结算之后又触发一次收尾），
   而不是继续加保险；
3. 顺带查一件事：`showResult` 里 `B.panel` 的赋值路径是不是被**第二次 `finish()`** 覆盖过
   （`finish()` 有 `B.done` 闸，所以只可能是**另一次 `BattleUI.run`**）。
